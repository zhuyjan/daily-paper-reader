## 摘要
智能体在长时程LLM系统中的自我进化本质上是程序性的：有用的经验不仅仅是存储的信息，而是可重用的搜索、调试和验证程序。然而，当前的评估并未将这种迁移形式独立出来。智能体基准测试的是单集任务解决能力；记忆基准测试针对信息保留而非程序重用。我们提出了EvoAgentBench，这是一个通过能力引导迁移进行智能体自我进化的基准测试，涵盖四个智能体领域：网络研究、算法推理、软件工程和知识工作。EvoAgentBench从智能体执行中提取基于轨迹的能力，将其规范化为操作单元，并构建跨共享程序重叠任务的领域特定能力图。通过设计，每个测试任务都有经过验证的训练侧能力支持。在528/267的训练/测试划分中，两种支架和三个骨干模型上，精心策划的能力内容在模型家族间可靠地迁移，但目前没有一种自动方法能在所有设置中保持正向增益。EvoAgentBench将自我进化评估从总体准确率比较转向对经验编码、路由和吸收的细粒度诊断。该基准测试公开于https://huggingface.co/datasets/EverMind-AI/EvoAgentBench。

## Abstract
Agent self-evolution in long-horizon LLM systems is largely procedural: useful experience is not merely stored information, but reusable procedures for searching, debugging, and verification. Yet current evaluations do not isolate this form of transfer. Agent benchmarks test single-episode task solving; memory benchmarks target information retention rather than procedural reuse. We introduce EvoAgentBench, a benchmark for agent self-evolution via Ability-guided transfer across four agentic domains: web research, algorithmic reasoning, software engineering, and knowledge work. EvoAgentBench extracts trace-grounded Abilities from agent executions, canonicalizes them into operational units, and builds domain-specific Ability Graphs linking tasks that share procedural overlap. By design, every test task is backed by verified training-side Ability support. Across a 528/267 train/test split, two scaffolds, and three backbones, curated Ability content transfers reliably across model families, but no current automatic method sustains positive gain in all settings. EvoAgentBench shifts self-evolution evaluation from aggregate accuracy comparison to fine-grained diagnosis of experience encoding, routing, and uptake. The benchmark is publicly available at https://huggingface.co/datasets/EverMind-AI/EvoAgentBench.

## 1. 核心问题与整体含义（研究动机和背景）

- **现状与空白**：现有智能体（LLM Agent）基准主要测试**单次任务解决能力**（如 SWE-Bench、LiveCodeBench）或**信息记忆能力**（如 LongMemEval），但无法评估智能体从过去经验中提取**可重用程序性知识**（如搜索策略、调试流程、验证步骤）并在新任务中迁移的能力。  
- **研究动机**：一个实用的智能体不应每次从零开始解决问题，而应能从历史轨迹中吸取可复用的过程性知识。这种 **“轨迹到程序”的迁移** 是智能体自我进化的核心，但现有基准缺乏针对性的评估。  
- **核心问题**：如何构建一个基准，既能保证测试任务与训练任务在能力层面足够相关（有可迁移的程序），又能防止单纯记忆或近重复暴露，从而**隔离并测量程序性迁移的效果**？

## 2. 方法论：核心思想、关键技术细节

### 2.1 核心思想
EvoAgentBench 基于 **“Ability Graph”（能力图）** 构建。基本单元是 **Ability（能力）**：从执行轨迹中提取的可重用操作（如搜索策略、调试程序、验证工作流），而非数据集标签或主题。任务之间的关系由共享的能力决定，数据划分也基于能力而非随机。

### 2.2 构建流程（三阶段）

1. **多骨干轨迹收集**：对每个任务，使用三个构造骨干（Kimi-K2.5、GLM-5.1、DeepSeek-V3.2）在无技能状态下执行，收集成功与失败轨迹。  
2. **基于轨迹的能力提取**：提取器（Claude Sonnet 4.6）联合分析多骨干轨迹，为每个任务生成原始能力卡片，每条卡片包含：触发条件、可重用程序、证据、边界、角色（方法/守卫/工作流）。  
3. **能力规范化与图构建**：  
   - 通过嵌入相似度进行阻塞、LLM 三裁判+领域专家复审进行合并，形成规范化的能力单元。  
   - 构建无向能力图：两个任务共享至少一个可边缘能力即连边。  
   - 使用 Louvain 社区检测划分社区，在社区内进行**受能力支持的数据划分**：每个测试任务必须与至少一个训练任务共享至少一个边缘能力（Ability-aware split）。最终得到528/267的训练/测试划分，零测试任务无训练侧支持。

### 2.3 评估指标
主要指标是平均迁移增益 \(\Delta_m = \frac{1}{|\mathcal{D}_{\text{test}}|} \sum_{x \in \mathcal{D}_{\text{test}}} (r_m(x) - r_0(x))\)，同时报告交互成本变化。所有方法使用相同的任务、工具集、超时和基础配置，仅进化状态不同。

## 3. 实验设计

- **数据集/场景**：四个长时程智能体领域：  
  - 网页研究：BrowseComp-Plus  
  - 算法推理：LiveCodeBench  
  - 软件工程：SWE-Bench Verified  
  - 知识工作：GDPVal  
  每个领域使用其原生评估协议（LLM裁判、隐藏测试、仓库测试等）。

- **基准与对比方法**：  
  - **无进化基线（Vanilla）**  
  - **三种自动自我进化方法**：  
    - **Memento**：检索最相似训练案例  
    - **ReasoningBank**：检索蒸馏推理记忆池  
    - **GEPA**：在训练集上进化一条提示并广播  
  - **诊断参考（Anchor Skill）**：使用策划侧能力-技能（由构造骨干从训练轨迹提取，利用测试任务的能力标签进行检索，但技能内容仅来自训练侧）。Anchor 不是可部署方法，而是测量能力内容是否可迁移的参考。

## 6. 主要结论与发现

1. **能力内容可跨模型家族迁移**：诊断参考 Anchor Skill 在所有6个支架-骨干设置、所有24个领域-设置单元格中均获得正增益，表明从不同构造骨干提取的能力内容可以提升来自不同模型家族的智能体。  
2. **自动方法仍不稳定**：三种自动方法在每个设置/领域均存在至少一个负迁移单元格。Memento 在 SWE 领域出现高达 -36.3% 的退化；ReasoningBank 虽平均为正，但仍有部分负增益；GEPA 表现随骨干变化大。  
3. **瓶颈在于方法侧**：由于任务、工具等固定不变，锚点与自动方法的差距归因于后者在经验编码、路由和吸收机制上的缺陷。  
4. **成本-准确性解耦**：进化并不总是降低成本。GEPA 和 Memento 在解决的任务上有时增加交互步数；成本变化因方法、支架、骨干而异，不能作为准确率的代理指标。

## 7. 优点

- **问题定义清晰**：首次将智能体自我进化定义为“轨迹到程序迁移”，并设计原则（能力支持但实例不重叠）来隔离测量。  
- **多层次构建方法**：从轨迹提取原始能力、三裁判规范、领域专家复审保证质量；能力图提供结构化的任务关系。  
- **多域多设置评估**：覆盖四个本质不同的智能体领域，使用两个支架、三个骨干（不同规模、不同家族），提高了结论的泛化性。  
- **诊断性参考设计**：Anchor Skill 作为上界参考，揭示了“能力内容可迁移 vs 自动方法提取/路由失败”的根本区别。  
- **细粒度诊断**：从总体准确率转向对编码、路由、吸收三阶段的诊断，为方法开发提供方向。  
- **公平性控制**：所有条件共享任务、工具、评分、超时；构造骨干与评估骨干解耦；避免信息泄露。

## 8. 不足与局限

- **构造骨干有限**：仅使用三个开放骨干，能力词汇可能受其影响。更丰富或不同的提取器可能导致不同能力集合，论文未探讨替代提取器的影响。  
- **测试集规模较小**：每个领域测试任务56-86个，虽然足够暴露模式级差异，但细粒度领域内分析受限。  
- **评估骨干可能受污染**：骨干模型可能在预训练时接触过源基准数据，但论文论证由于所有条件共享同一骨干，比较仍有效。  
- **绝对增益不可外推**：测试集偏向于构造骨干有提升空间的任务，因此观察到的 \(\Delta\) 大小不代表随机样本上的预期增益，仅用于方法间比较。  
- **未涉及多模态或具身智能体**：当前仅限文本智能体，扩展性有待验证。  
- **成本分析未纳入计算资源成本**：只报告了交互步数变化，未考虑技能库索引/检索的额外LLM调用成本。
